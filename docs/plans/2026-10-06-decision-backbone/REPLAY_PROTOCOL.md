# Future recurrent-maintenance comparison

Date: 2026-10-06. **Status: proposed protocol; not run.** This trial follows a
working local handoff implementation. It is separate from the completed
[format/selection experiment](../../inquiry/wedge-experiments-2026-10-06/PROTOCOL.md),
whose oracle-curated briefs and handcrafted links did not measure upkeep. None
of the thresholds below has been met by current evidence.

## Question and advancement decision

Does Foundry reduce the total work of creating, maintaining and resuming a
decision record compared with competent files and an index, while preserving
decision quality through repeated changes?

Run this comparison before investing in a specialized executor. Passing permits
a separately scoped executor evaluation; it does not establish customer demand,
cheap-model quality, cash savings or permission to spend. Failure can justify
retaining useful intake and correctness repairs while narrowing the product,
improving the handoff or choosing the file workflow. Do not respond to failure by
adding a model, more departments or a larger graph editor.

## Freeze the trial before execution

Use six new synthetic case pairs: local information service, software release,
physical supplier trial, outreach permission, pricing and customer pivot. Each
pair runs the same six-stage sequence below in both conditions. Agent-generated
world state supplies the facts and expected consequences; a separate critic
checks consistency before freezing. Include a plausible case where files should
be sufficient. These are invented scenarios, never real venture evidence.

Retain a versioned manifest with scenario/event hashes, hidden expected outcomes,
per-stage critical facts and scoring checks, model/provider/version/settings,
tool versions, context limits, starting state, timeout and retry limits, condition
order, fixed model price schedule and grading rules. Generate a new version for any change;
never overwrite a completed run's inputs. Neither executor sees future events or
the answer key. Grading agents cannot change expectations after seeing answers.

Agents own fixture generation, consistency review, operation and evidence
capture. The user is not asked to label data or perform a manual replay. Record
any human intervention that actually occurs; zero human time is valid only when
there was none.

There are 12 workflows: six cases multiplied by two conditions. Use the same
model and configuration for both members of each pair, isolated state, and a
fresh session at every stage; only persisted workspace material carries forward.
Counterbalance execution order: files first for cases 1, 3 and 5, Foundry first
for 2, 4 and 6. Do not let either session see its paired answer. This is a bounded
engineering comparison, not a statistically powered market study.

## Conditions and equal inputs

**Foundry:** the implemented map/context/result operations, concise agent view,
exact-record fetch and existing local console or CLI. Begin with source records
and an empty map; charge the work of making and maintaining the map and links.

**Files:** source files with stable IDs and revisions, a readable index, concise
current brief, decision/rationale history, work list and recent-arrivals list.
The agent can use ordinary search, scripted file updates and validation helpers
available before the run. Begin with the same source records and empty derived
documents; charge the work of creating and maintaining every summary and index.
Do not supply an oracle-selected brief or a pre-maintained index for free.

Both conditions receive identical evidence text, arrival order, task wording,
authority, initial work and permitted actions. They get the same executor model,
general search/read/write tools, wall-clock limits and recovery opportunities.
Condition-specific persistence operations are the intended difference. Freeze
helpers before the run; if a small file adapter already solves a requirement,
include it rather than handicapping the baseline. Any helper introduced during
execution invalidates that version's comparison and requires a new frozen run.

Application/helper development effort is not runtime upkeep. Disclose it
separately for both conditions; do not charge one product's historical development
against the other condition's replay. Charge all per-case configuration, schema
discovery, setup and agent instruction work needed to operate either condition.

## Fixed sequence in every case

Each stage ends with a saved current decision, cited rationale, affected and
unaffected work, unresolved questions and conditional next action. Exact facts
vary by case; the event structure and evaluation tasks remain fixed.

| Stage | Injected event and required work |
|---|---|
| 1. Initial creation | Give eight relevant source records and four historical/sibling records. Create the map or file/index state, establish the current decision and queue one bounded investigation. Produce the first resumable brief. Count all setup. |
| 2. Unlinked arrival and noise | Deliver one material new fact without a task/decision link, plus five unrelated same-workspace records. Resume, inspect/classify arrivals, update the affected rationale and leave unrelated work intact. No oracle identifies the relevant arrival for the executor. |
| 3. Correction and conflict | Correct one earlier source and add an independently supported contradictory source. Preserve the old version, distinguish correction from unresolved disagreement, and review dependent work. The frozen case may require hold or further investigation rather than choosing a convenient source. |
| 4. Pivot during outstanding work | Freeze a research request/result against the old scope, then change the intended customer or objective and its success conditions. Record what survives, what needs review and one unaffected work item. The old result remains withheld until stage 5. |
| 5. Late result and retries | Deliver that old-scope result. Retain its findings without applying obsolete effects, reconcile useful evidence through a fresh proposal, and resolve once. Repeat the identical submission/resolution, then try the same identity with changed content. Require one application of accepted effects and an explicit conflict for the changed payload. |
| 6. Restart and continuation | Close the session/process and reopen the persisted workspace in a fresh agent session. Reconstruct current scope, evidence, unresolved conflict, rationale and next work from stored records. Explain one stopped alternative and resume the authorized task without rebuilding history or reviving obsolete work. |

Freeze the withheld stage-5 result before the run; it is identical in each pair
and deliberately stale. It is an injected event, not a claimed output of either
executor. Creating the outstanding request and handling its return are measured
operational work. No network source changes, real outreach or live database edits
are required. A completed no-change, hold or stop decision can satisfy a stage.

## Fixed primary measurement

The primary metric is **total fixed-rate inference cost per completed workload**:
provider-reported billed token categories multiplied by a common price schedule
frozen before execution. The advancement threshold is a reduction of at least
20%. This protocol selects that metric now; a future agent cannot substitute a
time or payload metric because it gives a more favorable result.

For every operational call, retain provider/model/version, uncached input, cached
input, output and any other separately billed usage. Calculate
`sum(usage_category * frozen_price_per_unit)` across every call. Count setup,
prompts/system/tool payloads, outputs, bookkeeping, classification, searches and
fetches, retries, reconciliation, corrections and operational review. The same
model/version and price schedule apply to both conditions, with cache behavior
recorded and starting cache conditions controlled as far as the provider permits.
Record the source/date of that schedule and retain raw categories so the result
can be recalculated. Count each token once under the provider's usage definition;
do not double-count reasoning already included in billed output tokens.

Unreported billed categories make the measurement incomplete. Identical models
do not make bytes, tokenizer estimates or partial session usage equivalent to a
complete bill. This metric isolates inference expense at fixed prices: report
actual charges and any other source/tool/serving costs separately. It does not
establish whole-system profitability or a cash saving for subscription users.

Use the same collection method for both conditions. An instrumentation-only
smoke test on unrelated dummy material can verify telemetry before the main run.
Trial fixture generation
and independent scoring are evaluation overhead, reported separately for both;
ordinary result review and repairs needed to complete a task are operational
work. Their model calls belong in the primary metric and any human involvement
belongs in the time/intervention record. Permit an initial attempt and at most two
recovery attempts per stage within a frozen time cap. Count every failed attempt.

Normalize each condition's total by **36 required stage outcomes** (six cases
times six stages), including initial creation. Also report unnormalized totals,
setup versus later upkeep, each paired case and each stage. An unfinished outcome
does not disappear from the denominator and prevents the run passing.

If complete billed usage or the price schedule is unavailable, report the primary
result as unavailable and the cost gate as inconclusive. Do not estimate the
missing bill from bytes, tokenizer output or tool calls. Do not substitute time
or declare the gate passed on convenience grounds.

Record agent execution seconds and active human assistance/review seconds as
secondary measurements. Include tool waits and failed attempts, exclude gaps
between scheduled stages, sum worker seconds when agents run in parallel, and
count each human activity interval once. Retain both components and end-to-end
elapsed time. Human effort cannot disappear merely because the primary metric is
inference cost: explain any shift of work from agents to people. An increase in
human intervention requires a separate time-value assessment before advancement.
An optional future time-value trial must freeze its own primary metric and
threshold before running; it cannot retroactively rescue this cost gate.
Bytes/words, tool calls, fetch counts, bookkeeping interventions and estimated
tokens are secondary diagnostics only.

## Quality and pass thresholds

Before execution, define eight binary checks per stage: correct current scope,
material supporting facts, material counterevidence/uncertainty, source/version
attribution, justified disposition, exact affected work, preservation of unrelated
work/authority, and retrievable rationale/history. The rubric specifies the
expected facts and acceptable alternatives, not preferred wording. Score outputs
blind to condition where feasible; retain any unavoidable unblinding and critic
disagreements. Resolve grading disagreements from the frozen rubric and sources.

A critical failure is an unflagged omission of a decision-critical fact in a
context declared decision-ready; an authoritative conclusion that ignores such
a fact or known unresolved coverage; a wrong-scope/unauthorized effect; an obsolete
result changing current state; duplicated accepted effects; or lost evidence or
decision history. A visibly incomplete proposal that correctly stops for required
inspection is not itself critical, but inspection and recovery count as work.

Advance only when **all** of these predeclared conditions hold:

1. Foundry completes all 36 stage outcomes with zero critical failures.
2. Foundry meets at least 95% of the 288 binary quality checks and is no more than
   two percentage points below the file condition. Report first-attempt errors
   as well as final quality; recovery never erases a critical failure.
3. Foundry's aggregate normalized primary measurement is at most **80%** of the
   file condition's, and Foundry uses less primary work in at least four of the
   six paired cases. All setup and subsequent upkeep remain included.
4. The file baseline completes all outcomes, has zero critical failures and meets
   at least 95% of checks. If it does not, the comparison has not established an
   adequate baseline: repair it and freeze a new run, rather than claim a victory
   over a broken alternative.

These are engineering advancement thresholds selected before measurement, not
confidence intervals or universal market requirements. Report failed cases and
cases where files win. A quality pass without the primary reduction does not
pass the combined gate; an efficiency win with weaker safety does not pass it.

## Retained result and next action

Save inputs/hashes, exact commands and versions, frozen price schedule,
operational transcripts/artifact references, usage/timing records, every attempt,
blind scores and disagreements, per-case comparisons and pass/fail/inconclusive
status in a new dated run directory. Keep synthetic material outside the real
venture store and avoid sensitive payload logs. Include a brief reproducible
walkthrough; do not turn missing evidence into an assignment for the user.

On pass, propose a bounded source-change executor evaluation with its own held-out
quality/cost contract. On failure, record whether creation, classification, link
maintenance, fetching, result review or baseline adequacy explains the result;
make only a justified narrow change before another frozen comparison. On missing
telemetry or blocked execution, report the exact unmeasured gate. Existing local
repairs may remain useful in every outcome. This protocol itself authorizes no
paid model calls, training, hosting or external actions.
