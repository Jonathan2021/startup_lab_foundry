# Scoring and evidence calibration — revision 2

The workbook's scalar scores are preserved as source data, not reused as build
recommendations. They mixed subjective estimates with unverified competitor
analogues. This campaign uses decision gates and an evidence vector instead of
pretending the current tiny sample can fit a business-success prediction model.

These are judgement/rule revisions, **not statistically learned weights**. There
are no paid-user outcome labels, conversion rates or validated market-size inputs.
Do not claim calibration of willingness to pay from four technical probes.

## Evidence vector for every candidate

Keep distinct fields for: source reliability/claim scope; exact comparator match;
tested capability; accessible permitted inputs; repeated workflow pain; buyer and
distribution access; cost/support burden; and learning fit. Unknown stays unknown.

Order the next work by the value of reducing an uncertainty cheaply, rather than
by a fabricated financial score. A physical idea can receive an access hold
without being declared a bad business. A useful incumbent can remove the reason
to write code while leaving a service or specialist integration opportunity open.

The three new-idea survivor hypotheses are scoped discovery candidates:
mixed-route constraints (public engine/data and a specific reported annoyance),
physical-task verification (ground-truth/task access needed), and portable skill
evidence (issuer/buyer access needed). Internal source-impact work is a separate
Foundry need and has not earned a standalone venture designation.

## What counts as repeated demand

Two APIs missing the same display field in Foundry justify investigating our
internal read path. They do not demonstrate two customers for a SaaS product.
Two separate first-person reports can motivate a targeted test, but a selected
forum thread is not a prevalence estimate. Repeated source references, generated
suggestions, copied feature lists and duplicate ideas never raise demand confidence.

Before a substantial build, retain recent independently observed instances of
the same job, a comparison against a configured incumbent and a small script,
usable data, an adopter commitment and a credible buyer/distribution path. The
exact threshold is a working decision policy, not a universal startup law.

## Revision 3 — relevance audit and first-party task

The initial broad group links overstated source coverage. A second audit removed
unrelated links (for example, mouth-taping/physio references from wound scanning
and bird identification references from generic product lookup) and researched
closer comparisons. Revision 1 remains available with the exact inputs to T3/T6.
Current per-idea references are authoritative; group sources do not inherit.

N008 gained a concrete user task: a scenic motorcycle day with a time budget,
GPX/ETA disagreement, and rain-driven replanning. It now has stronger problem
evidence than a feature wish. Focused search also found closer incumbent and
newer-product overlap. This raises its priority for a workflow comparison while
**not** raising commercial-build readiness. First-party interest plus selected
forum accounts is not a prevalence estimate or payment evidence.

T5 failed because the API requests/coordinates did not yield routes. It is not
an incumbent-capability failure. T6 passed exact-link controls, but the relevance
audit showed that accurate joins can still propagate irrelevant references.
Source/claim relevance must be reviewed before reusing or invalidating decisions.
