# Derived candidates from the next comparisons

Date: 2026-10-02. These are explicit rescopings, not independent demand signals.
The original portfolio and previous dispositions remain intact. Each draft is
stored as an Idea with parent links; none is automatically promoted to a build.

## D001 — GPX transfer preflight

Parent: N008. User: a touring rider moving a carefully shaped ride between planners.
Job: identify changed road sections and distinguish changed geometry from a changed
ETA convention before relying on the transferred plan. Possible form: a small
open-source diagnostic or integration, with paid support only if a buyer emerges.

Counterevidence: [RouteConverter](https://www.routeconverter.com/) already offers
format conversion, editing and simultaneous visible position lists.
[gpx.studio](https://gpx.studio/app) is an existing browser GPX editor and a candidate
visual comparison baseline. Generic conversion/overlay is therefore a weak new
product premise. A bounded synthetic comparison is recorded separately; it cannot
explain the user's historical mismatch. Next gate: a specified route/files and a
reproducible diagnostic miss that matters to the rider. See R001 in the inbox.

## D002 — source-linked decision review queue

Parents: G002, P088, P174. User: a team maintaining decisions that depend on changing
external capability or policy claims. Job: review only the decisions linked to a
changed claim, retaining the old evidence and the resolution. Possible form: an
integration on top of an existing monitor, initially used internally by Foundry.

Counterevidence: [Distill's change history](https://distill.io/docs/web-monitor/change-history-and-highlighted-changes/)
already retains changes with visual/text comparison. Its
[configuration documentation](https://distill.io/docs/web-monitor/config-and-advanced-monitor-options/)
also specifies an explicit empty-selection error. Generic history, diffing or
missing-selector alerts are not an established gap. Our prior exact-link exercise
already supplied simple dependency mapping with ordinary files. Keep internal;
reopen a commercial build only when a real external user repeatedly needs the
claim-to-decision workflow and rejects an incumbent-plus-small-script baseline.

## D003 — portable work-sample receipt

Parents: N003, G005, P106. User: an organization sharing a bounded assessment result
with a candidate and another decision-maker. Job: carry the exercise, rubric,
evidence, evaluator and limits without implying a universal skill score.
Possible form: an Open Badges integration or service-assisted issuing workflow.

Counterevidence: [Open Badges' own FAQ](https://openbadges.org/about/faq) already
includes issuer, criteria and achievement evidence. The
[3.0 specification](https://www.imsglobal.org/spec/ob/v3p0/) defines verifiable
achievement credentials and evidence. A new credential format is not justified.
The unresolved issue is institutional acceptance of a particular exercise, not
whether a signed JSON object can carry evidence. Hold platform implementation
until an issuer and recipient will test it; see R003.

## What changed

Three smaller jobs can be named, but competition further reduces broad-build
novelty. D001 remains an input-dependent diagnostic investigation, D002 an internal
Foundry workflow, and D003 an access-dependent integration/adoption test. No market
size, willingness-to-pay or new scoring weights are inferred from these sources.
This round supplies real counterevidence and clearer stops, not a manufactured
winner. New-source checks are documentary unless their separate trial says otherwise.
