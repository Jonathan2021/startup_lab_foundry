# Foundry product boundary review

Date: 2026-10-06. Planning and read-only verification; no application changes,
live record changes, external actions, or implementation authorization.

## Questions and competing explanations

1. Do the claimed revamp repairs address the recorded failures? Inspect the
   relevant code and run focused existing tests using disposable data. Keep
   functional checks separate from browser acceptance. A passing test suite is
   not proof that the product scope is useful.
2. Is Foundry's valuable unit a portfolio, a venture, or the continuity of
   evidence and decisions across human and agent work? Compare portfolio-only,
   venture-only, and an integrated product with explicit ownership boundaries.
3. Should task execution belong to the user's agent, a Foundry runner, or both?
   Compare a shared task/result contract against building an agent platform.
4. Does the proposed distinction survive current alternatives and ordinary
   files plus an agent? Vendor capabilities are evidence of available alternatives,
   not customer demand or independent product-quality validation.

## Bounded method

- Read the original brief, current direction, architecture, prior review and new
  repair report. Preserve their definitions and historical status.
- Delegate an independent repair spot check, a primary-source landscape scan,
  and a critique grounded in current venture friction.
- Inspect official agent/tool integration and adjacent product sources. Record
  what was actually established, source limits, and strategic inferences.
- Recommend one initial user and recurring job, ownership and execution rules,
  a legible interface, scope exclusions, and a small falsifiable validation plan.
- Keep architecture recommendations proposed. No schema rewrite, framework,
  hosted agent, migration, or commercial viability claim follows from this review.

## Decision criteria

The proposal must explain the Crous next-step workflow, sports fusion, and shared
outreach without duplicate truth or hidden execution. It must support one venture
without requiring a portfolio, and a user's agent without requiring a Foundry
model. It must state when existing tools are sufficient and what observation
would justify the next narrow implementation.
